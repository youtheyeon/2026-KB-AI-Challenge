# 사업 상태 분석 및 병목 진단 API 설계

## 목표

정규화가 완료된 사업 데이터와 고정된 서울시 카페 공공데이터 벤치마크를 분석해 사업 지표와 병목 후보를 생성한다. 진단 실행은 FastAPI `BackgroundTasks`로 요청 처리와 분리하고, 실행 상태와 결과를 기존 진단 도메인 모델에 보존한다.

## API 계약

### 진단 실행

`POST /api/businesses/{businessId}/diagnoses`는 `datasetId`를 받아 다음 순서로 처리한다.

1. 익명 데모 세션이 사업장을 소유하는지 확인한다.
2. 데이터셋이 요청한 사업장에 속하고 `READY` 상태인지 확인한다.
3. 분석 기준 월의 사업 스냅샷과 공공데이터 스냅샷을 생성한다.
4. `RUNNING` 상태의 진단을 저장하고 트랜잭션을 커밋한다.
5. 커밋된 진단 ID를 `BackgroundTasks`에 전달한다.
6. `diagnosisId`, `businessId`, `RUNNING`, `createdAt`을 `202`로 반환한다.

소유하지 않은 사업장이나 다른 사업장의 데이터셋은 존재 여부를 노출하지 않도록 `404`로 처리한다. 요청 본문이 올바르지 않으면 `400`을 반환한다. 데이터셋이 `READY`가 아니면 `409`와 `DATASET_NOT_READY` 오류를 반환한다.

### 진단 조회

`GET /api/diagnoses/{diagnosisId}`는 진단에 연결된 사업장의 익명 데모 세션 소유권을 확인한다.

- `RUNNING`과 `FAILED` 상태에서는 결과 객체를 `null`로 반환한다.
- `COMPLETED` 상태에서는 재무 지표, 사업 활동 지표, 상권 지표, 병목 후보를 반환한다.
- 진단이 없거나 다른 세션 소유이면 `404`와 `DIAGNOSIS_NOT_FOUND` 오류를 반환한다.

외부 API의 상태 문자열과 병목 우선순위·신뢰도는 대문자 문자열을 사용한다.

## 실행 구조

라우터는 인증·입력 검증·응답 변환만 담당한다. 진단 서비스는 스냅샷 생성, 지표 계산, 병목 판정, 영속화를 담당한다. 벤치마크 로더는 백엔드에 포함된 작은 JSON 스냅샷만 읽으며 진단 요청 중 외부 API를 호출하지 않는다.

백그라운드 작업은 요청에서 사용한 SQLAlchemy 세션을 재사용하지 않고 `SessionFactory`로 새 세션을 연다. 계산과 결과 저장을 하나의 트랜잭션으로 처리하고 성공하면 `COMPLETED`로 변경한다. 예외가 발생하면 트랜잭션을 롤백한 뒤 별도 트랜잭션에서 진단 상태를 `FAILED`로 변경하고 예외를 기록한다.

FastAPI 프로세스가 종료되면 실행 중 작업이 유실될 수 있다. 영속 작업 큐와 멈춘 `RUNNING` 진단 복구는 이번 범위에서 제외한다.

## 분석 기준 월

데이터셋의 `NormalizedSale.business_date` 중 가장 최신 날짜가 속한 달을 분석 기준 월로 사용한다. 매출, 비용, 온라인 매출은 모두 같은 연월의 행만 집계한다.

매출 행이 없거나 월매출이 0 이하라 계산을 수행할 수 없으면 백그라운드 진단을 `FAILED`로 변경한다.

## 사업 지표 산식

### 재무 지표

- `monthlySalesAmount`는 기준 월 `net_sales` 합계다.
- `operatingProfitRate`는 `(월매출 - 월비용) / 월매출 × 100`이다.
- `materialCostRate`는 재료비 분류 비용 합계 `/ 월매출 × 100`이다.
- `cashSurplusAmount`는 `월매출 - 월비용 - 기존 월 상환액`이다. 기존 월 상환액은 최초 진단에서 0을 사용한다.

### 사업 활동 지표

- `monthlyOrderCount`는 영수증 번호가 있으면 고유 영수증 수를 사용하고, 모두 없으면 매출 행 수를 사용한다.
- `onlineSalesRatio`는 온라인 자료가 있을 때 `온라인 sales_amount 합계 / 월매출 × 100`으로 계산한다. 자료가 없으면 `null`이다.
- `employeeCount`는 사업장 기본 정보의 직원 수다.

### 상권 지표

- `salesComparedToPeerRate`는 `(월매출 / 최신 분기 서울 카페 월매출 중앙값 - 1) × 100`이다.
- `floatingPopulationGrowthRate`는 현재 캐시 데이터에 유동인구가 없으므로 `null`이다.

계산 비율은 API에서 퍼센트 단위로 반환하고 소수점 첫째 자리까지 반올림한다. 금액은 원 단위 정수로 반환한다.

## 공공데이터 벤치마크

런타임에는 `ai/raw_data/seoul_cafe_sales_full.json` 전체를 직접 읽지 않는다. 해당 원본의 최신 분기에서 다음 값만 계산한 버전 고정 JSON을 백엔드에 포함한다.

- 기준 분기와 기준일.
- 출처명과 스냅샷 버전.
- 서울 카페 표본 수.
- 월매출 중앙값.
- 월주문 중앙값.
- 시간대별 매출 비중.

진단마다 사용한 값을 `PublicDataSnapshot.raw_data`에 복사해 이후 벤치마크 파일이 갱신돼도 과거 결과의 근거를 재현할 수 있게 한다. `reference_area`는 `서울 전체 커피-음료 상권`으로 기록한다.

## 병목 판정

기존 `ai/bottleneck_detector.py`의 비율 기준과 세 단계 심각도 개념을 백엔드 입력 구조에 맞게 적용한다.

- 재료비율은 기준 42%보다 높은 격차가 5%p, 10%p, 15%p에 도달할 때 각각 `MILD`, `CLEAR`, `SEVERE`로 판정한다.
- 인건비율은 기준 20%보다 높은 격차가 5%p, 10%p, 15%p에 도달할 때 각각 `MILD`, `CLEAR`, `SEVERE`로 판정한다.
- 온라인 자료가 있을 때 온라인 매출 비중이 기준 20%보다 낮은 격차가 5%p, 10%p, 15%p에 도달하면 각각 `MILD`, `CLEAR`, `SEVERE` 판매 채널 편중 후보로 판정한다.
- 온라인 자료가 있을 때 플랫폼·결제·점주 부담 배달비 합계 비율이 기준 15%보다 높은 격차가 5%p, 10%p, 15%p에 도달하면 각각 `MILD`, `CLEAR`, `SEVERE` 플랫폼 비용 후보로 판정한다.
- 온라인 자료가 있을 때 취소·환불률이 기준 5%보다 높은 격차가 5%p, 8%p, 12%p에 도달하면 각각 `MILD`, `CLEAR`, `SEVERE` 취소·환불 후보로 판정한다.
- 온라인 자료가 있고 정산금액이 있을 때 순정산율이 기준 92%보다 낮은 격차가 5%p, 10%p, 15%p에 도달하면 각각 `MILD`, `CLEAR`, `SEVERE` 낮은 정산율 후보로 판정한다.
- 거래 시간이 있는 매출액이 월매출의 80% 이상이면 사용자 시간대별 매출 비중을 캐시된 시간대별 벤치마크와 비교한다. 벤치마크보다 낮은 상대 격차가 15%, 35%, 60%에 도달하면 각각 `MILD`, `CLEAR`, `SEVERE`로 판정한다. 80% 미만이면 시간대 병목을 만들지 않는다.

API 우선순위는 `MILD`, `CLEAR`, `SEVERE`를 각각 `LOW`, `MEDIUM`, `HIGH`로 변환한다. 직접 업로드 데이터와 공공데이터 비교는 `HIGH`, 업계 가정치가 포함된 비교는 `MEDIUM` 신뢰도로 반환한다.

자료가 없다는 이유만으로 병목을 만들지 않는다. 온라인 자료가 없으면 온라인 관련 병목 전체를 생략한다.

## 영속화

기존 모델과 초기 마이그레이션에 필요한 테이블과 컬럼이 이미 있으므로 새 마이그레이션을 만들지 않는다.

- `BusinessSnapshot`에는 기준 월의 사업 지표와 데이터셋 관계를 저장한다.
- `PublicDataSnapshot`에는 실제 사용한 벤치마크와 출처 메타데이터를 저장한다.
- `Diagnosis`에는 상태, 버전, 두 스냅샷 관계를 저장한다.
- `DiagnosisMetric`에는 API 지표와 비교값, 차이, 단위, 출처를 저장한다.
- `Bottleneck`에는 병목 코드, 상세 근거, 심각도, 근거 출처를 저장한다.

동일 사업장과 데이터셋의 `BusinessSnapshot`은 기존 유일 제약에 맞춰 재사용한다. 같은 데이터셋으로 진단을 다시 실행할 수 있으며 새 `Diagnosis`와 결과 행을 생성한다.

## 오류와 트랜잭션

- 요청 검증 실패는 `400`.
- 사업장·데이터셋·진단이 없거나 세션 소유권이 없으면 `404`.
- 데이터셋이 `READY`가 아니면 `409 DATASET_NOT_READY`.
- 시작 트랜잭션이 실패하면 진단 행을 남기지 않는다.
- 백그라운드 계산 트랜잭션이 실패하면 지표와 병목을 남기지 않고 진단만 `FAILED`로 변경한다.

오류 응답은 Notion 명세의 `{"error": {"code": "...", "message": "..."}}` 형태를 사용한다.

## 테스트

- 순수 계산 테스트로 기준 월 선택과 모든 지표 산식을 검증한다.
- 병목 테스트로 경계값, 자료 부재 시 생략, 심각도·우선순위·신뢰도 변환을 검증한다.
- API 테스트로 `202/RUNNING`, `COMPLETED`, `FAILED`, `400`, `404`, `409` 계약을 검증한다.
- 세션 테스트로 다른 익명 데모 세션의 사업장과 진단을 조회할 수 없는지 검증한다.
- PostgreSQL 통합 테스트로 스냅샷, 진단, 지표, 병목이 한 트랜잭션으로 저장되는지 검증한다.
- 격리된 `TEST_DATABASE_URL`이 있을 때만 파괴적 통합 테스트를 실행하며 Supabase 운영 DB에는 테스트 스키마 초기화를 수행하지 않는다.

## 제외 범위

- Celery, RQ, Redis 등 영속 작업 큐.
- 실행 중 작업 재시도와 서버 재시작 후 복구.
- 진단 요청 중 공공데이터 API 실시간 호출.
- 유동인구 데이터 추정 또는 다른 지표를 유동인구로 대체하는 처리.
- `ai/` 전체의 패키지화와 mock 전용 진단 코드 리팩터링.
