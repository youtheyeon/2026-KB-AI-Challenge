## 프로젝트 소개

SCB가 소상공인의 미래 성장성을 평가해 금융 기회를 넓힌다면, 이 프로젝트는 확보한 자금이 실제 성장과 안정적인 상환으로 이어지도록 돕습니다.

사업자의 매출·비용·온라인 판매 데이터를 분석해 현재 사업의 병목 후보를 찾고, 대출자금을 활용할 수 있는 A·B·C 배분안을 동일한 기준으로 비교합니다.

사용자가 배분안을 직접 선택하고 자금을 집행한 뒤에는 실제 성과를 기록해 예상과의 차이를 확인합니다. 완료된 결과는 다음 시뮬레이션의 초기 조건과 배분 근거에 다시 반영됩니다.

이 서비스는 특정 배분안을 추천하거나 매출 성장을 보장하지 않습니다.

AI와 계산 모델은 판단에 필요한 병목, 배분 근거, 상환 부담과 손익분기 조건을 제공합니다. 최종 결정은 사용자가 내립니다.

## 해결하려는 문제

소상공인은 대출을 받은 이후에도 다음 질문을 스스로 해결해야 합니다.

- 마케팅, 설비, 인력, 재고 중 어디에 우선 투자해야 하는가.
- 현재 사업에서 가장 먼저 해결해야 할 병목은 무엇인가.
- 월 상환액과 추가 비용을 감당하려면 얼마의 매출이 더 필요한가.
- 계획대로 자금을 집행한 뒤 실제 성과는 예상과 얼마나 달랐는가.
- 이번 결과를 다음 자금 계획에 어떻게 반영해야 하는가.

KB 소상공인 금융 지원 에이전트는 자금의 계획, 선택, 집행, 검증을 하나의 반복 가능한 흐름으로 연결합니다.

## 핵심 사용자 흐름

~~~mermaid
flowchart LR
    A["사업 정보 및 매출·비용 데이터 연결"] --> B["사업 상태와 병목 후보 진단"]
    B --> C["대출 조건 입력"]
    C --> D["A·B·C 자금 배분안 생성"]
    D --> E["재무 결과와 위험 비교"]
    E --> F["사용자 직접 선택"]
    F --> G["실제 자금 집행"]
    G --> H["90일 후 실제 성과 입력"]
    H --> I["예상 대비 결과와 병목 변화 검증"]
    I --> J["다음 시뮬레이션 조건 갱신"]
~~~

## 주요 기능

### 사업 현황 및 병목 진단

매출, 비용, 주문, 온라인 판매 데이터를 분석하고 공공데이터 및 비교 기준과 대조합니다.

진단 결과에는 병목 유형뿐 아니라 다음 정보가 함께 제공됩니다.

- 병목의 심각도.
- 사용자 사업장의 현재 지표.
- 비교한 기준값.
- 근거 데이터의 출처.
- 판정에 사용한 방법론.
- 근거에 따른 신뢰도.
- 관련 자금 배분 영역.

### A·B·C 자금 배분안 비교

진단된 병목을 기반으로 세 가지 관점의 배분안을 생성합니다.

| 배분안 | 기준 |
|---|---|
| A안 | 가장 뚜렷한 병목에 자금을 집중합니다. |
| B안 | 여러 병목의 심각도에 비례해 자금을 배분합니다. |
| C안 | 마케팅·설비·인력·재고에 균등하게 배분하는 비교 기준선입니다. |

AI는 특정 안을 추천하지 않습니다.

사용자는 각 배분안의 근거, 상환 부담, 손익분기 조건과 위험을 비교한 뒤 원하는 안을 직접 선택합니다.

### 설명 가능한 재무 시뮬레이션

검증되지 않은 매출 성장률을 정답처럼 예측하지 않습니다.

입력한 대출 조건과 자금 배분 계획을 기준으로 다음 값을 계산합니다.

- 대표 월 상환액.
- 추가 월 고정비.
- 상환 후 잔여 현금.
- 손익분기에 필요한 추가 매출.
- 필요한 추가 주문 수.
- 매출 감소 허용 범위.
- 사업 규모 대비 대출 부담.
- 재무 위험 수준과 판정 근거.

원리금균등, 원금균등, 만기일시 상환과 거치 기간을 지원합니다.

### 실제 집행 및 결과 검증

시뮬레이션에서 선택한 안과 실제 집행이 달라도 기록할 수 있습니다.

집행 후 성과 데이터는 다음 방식으로 입력할 수 있습니다.

- Mock 데이터로 체험.
- 매출·비용 XLSX 파일 업로드.
- 월 매출, 영업이익, 온라인 주문 비중과 상환 후 현금 직접 입력.

입력된 성과를 목표값 및 손익분기값과 비교하고 해결된 병목, 지속된 병목, 새로 발생한 병목을 구분합니다.

데이터가 부족한 지표는 임의의 값으로 채우지 않고 `NOT_COMPARABLE`로 처리합니다.

### 선순환 대시보드

완료된 결과는 다음 시뮬레이션에 다시 반영됩니다.

- 회차별 시뮬레이션과 실제 집행 이력.
- 사전·사후 핵심 지표 변화.
- 해결되지 않은 병목.
- 새로 발생한 병목.
- 다음 회차에서 우선 확인할 조건.
- 대출 상환 추정 현황.

회차가 쌓이면 반복되는 병목과 과거 배분 이후 발생한 부작용을 다음 자금 계획에서 다시 확인할 수 있습니다.

## AI 모델링

이 프로젝트의 AI는 하나의 블랙박스 모델이 모든 결정을 내리는 구조가 아닙니다.

비지도학습, 규칙 기반 진단, 결정론적 자금 배분, 재무 계산과 LLM 설명을 역할별로 분리했습니다. 각 단계의 입력과 출력, 판단 기준을 확인할 수 있어 결과가 만들어진 과정을 추적할 수 있습니다.

~~~mermaid
flowchart LR
    A["사업자 POS·매출·비용 데이터"] --> B["사업 지표 정규화"]
    P["서울시 상권분석 데이터"] --> C["상권 벤치마크"]
    B --> D["병목 진단 모델"]
    C --> D
    D --> E["A·B·C 자금 배분 모델"]
    E --> F["대출·재무 계산 모델"]
    F --> G["LLM 설명 생성"]
    G --> H["사용자 선택"]
    H --> I["실제 집행·성과 데이터"]
    I --> J["결과 검증 및 다음 회차 반영"]
~~~

### 현재 서비스에서 사용하는 모델

| 단계 | 방법 | 역할 | 주요 출력 |
|---|---|---|---|
| 데이터 전처리 | XLSX 자동 컬럼 매핑과 월별 집계 | 매출·비용 데이터를 공통 형식으로 변환 | 월 매출, 비용, 주문 수, 시간대별 매출 |
| 비교 기준 생성 | 최신 분기 상권 통계의 중앙값과 비중 계산 | 서울 카페 상권의 비교 기준 제공 | 매출 중앙값, 주문 수 중앙값, 시간대별 매출 비중 |
| 병목 진단 | 임계값 기반 설명 가능한 판정 모델 | 사업 지표와 비교 기준 사이의 차이를 판정 | 병목 유형, 심각도, 근거 출처 |
| 자금 배분 | 심각도 가중치 기반 결정론적 모델 | 병목을 네 가지 자금 카테고리로 변환 | A·B·C 자금 배분안 |
| 재무 시뮬레이션 | 대출 상환 및 손익분기 수식 | 현재 매출로 계획을 감당할 수 있는지 계산 | 월 상환액, 잔여 현금, 손익분기 매출 |
| 설명 생성 | Claude Haiku 기반 LLM | 계산 결과와 배분 근거를 자연어로 설명 | 배분 근거, SCB 관련 방향성 |
| 결과 검증 | 사전·사후 지표 비교 모델 | 실제 성과와 저장된 기준을 비교 | 해결·지속·신규 병목 |
| 회차 반영 | 과거 병목과 집행 이력 기반 규칙 | 반복 병목과 과거 부작용 반영 | 최소 배분 비중, 부작용 경고 |

### 1. 데이터 모델링

현재 백엔드 진단 API는 서울시 상권분석서비스의 커피·음료 업종 데이터를 사전 가공한 벤치마크를 사용합니다.

- 기준 분기는 `2024년 2분기`입니다.
- 비교 가능한 카페 상권은 `326개`입니다.
- 월 매출과 월 주문 수는 이상치 영향을 줄이기 위해 중앙값을 사용합니다.
- 시간대별 매출은 전체 매출에서 각 시간대가 차지하는 비중으로 변환합니다.
- 현재 캐시에 없는 유동인구 지표는 임의로 생성하지 않고 `null`로 처리합니다.

사용자의 매출·비용 데이터는 가장 최근 월을 기준으로 집계합니다. 온라인 판매 자료가 없으면 온라인 관련 지표와 병목을 만들지 않습니다.

### 2. 상권 소비 패턴 클러스터링

`ai/` 연구 파이프라인에는 서울 카페 상권을 소비 패턴에 따라 자동 분류하는 K-means 비지도학습 모델이 구현되어 있습니다.

상권명이나 행정구역 이름은 모델 입력에 사용하지 않습니다. 각 상권을 다음 13개 특성으로 표현합니다.

- 시간대별 매출 비중 6개.
- 요일별 매출 비중 7개.

~~~text
상권별 원본 매출
    ↓
여러 분기의 시간대·요일별 매출 비중 계산
    ↓
13차원 소비 패턴 벡터 생성
    ↓
StandardScaler 표준화
    ↓
K-means 군집화
    ↓
유사 소비 패턴 상권군 생성
~~~

모델은 `k=3~6`을 비교하고 실루엣 점수가 가장 높은 군집 수를 선택합니다.

현재 저장된 모델링 결과는 다음과 같습니다.

| 항목 | 결과 |
|---|---|
| 원본 매출 레코드 | 1,313건 |
| 군집화된 상권 | 342개 |
| 입력 특성 | 13개 |
| 선택된 군집 수 | 3개 |
| 실루엣 점수 | 0.228 |
| 재현성 설정 | `random_state=42`, `n_init=10` |

실루엣 점수 `0.228`은 군집 사이의 분리가 강하지 않다는 뜻입니다.

따라서 이 결과를 정답 분류로 사용하지 않고, 비슷한 소비 패턴을 가진 상권군을 찾기 위한 참고 모델로 사용합니다.

현재 통합 백엔드 진단 API는 안정적인 재현성을 위해 서울 전체 326개 상권 벤치마크를 사용합니다. K-means 기반 유사 상권군 비교는 `ai/run_simulation.py`의 연구 파이프라인에 구현되어 있으며, 운영 진단 API와의 완전한 연결은 후속 작업입니다.

### 3. 병목 진단 모델

병목 진단은 미래 매출을 예측하는 모델이 아니라 비교 가능한 판정 모델입니다.

사용자의 현재 지표와 공공데이터 또는 명시적인 업계 참고치를 비교해 격차를 계산하고, 그 크기에 따라 `경미`, `뚜렷`, `심각`으로 분류합니다.

진단 가능한 병목은 다음과 같습니다.

- 특정 시간대 고객 유입 부족.
- 높은 재료비 원가율.
- 높은 인건비 비중.
- 낮은 재구매율.
- 좌석 및 처리 용량 부족.
- 낮은 온라인 판매 비중.
- 높은 플랫폼 비용률.
- 높은 온라인 취소·환불률.
- 낮은 온라인 순정산율.

예를 들어 시간대별 매출 병목은 다음 기준으로 판정합니다.

~~~text
상대 격차
= (벤치마크 비중 - 사용자 비중) / 벤치마크 비중

15% 이상 차이 → 경미
35% 이상 차이 → 뚜렷
60% 이상 차이 → 심각
~~~

각 진단 결과에는 판정만 제공하지 않고 다음 정보도 함께 저장합니다.

- 실제 사용자 지표.
- 비교한 기준값.
- 두 값의 차이.
- 근거 데이터의 출처.
- 판정에 사용한 방법론.
- 근거에 따른 신뢰도.
- 대응 가능한 자금 카테고리.

실제 데이터와 업계 가정치를 같은 신뢰도로 다루지 않습니다. 공공데이터, 개인 실측값, 업계 가정치와 시연용 합성 데이터를 구분해 표시합니다.

### 4. 자금 배분 모델

병목 진단 결과는 다음 네 가지 자금 카테고리로 변환됩니다.

~~~text
마케팅·온라인
설비·인테리어
인력
재고
~~~

병목의 심각도는 다음 점수로 변환합니다.

~~~text
경미 = 1점
뚜렷 = 2점
심각 = 3점
~~~

같은 카테고리에 연결된 병목 점수를 합산한 뒤 세 가지 배분안을 생성합니다.

#### A안 · 병목 집중형

가장 높은 점수를 받은 카테고리에 남은 자금을 집중합니다. 모든 카테고리에는 기본적으로 최소 5%를 배정합니다.

#### B안 · 진단 비례 대응형

발견된 모든 병목의 심각도 점수에 비례해 자금을 나눕니다.

~~~text
카테고리 배분 비중
= 기본 최소 비중
+ 배분 가능 잔여 비중 × 카테고리 점수 / 전체 점수
~~~

#### C안 · 균등 분산형

진단 결과와 관계없이 네 카테고리에 각각 25%를 배분합니다. A안과 B안을 비교하기 위한 기준선입니다.

AI는 세 배분안의 우열을 정하거나 특정 안을 추천하지 않습니다. 사용자가 각 안의 근거와 재무 결과를 비교한 뒤 직접 선택합니다.

### 5. 재무 계산 모델

재무 모델은 “자금을 투입하면 매출이 몇 퍼센트 성장한다”는 값을 만들지 않습니다.

현재 매출이 그대로 유지된다는 보수적인 조건에서 대출 상환액과 추가 비용을 감당할 수 있는지 계산합니다.

핵심 계산은 다음과 같습니다.

~~~text
기준 월이익
= 현재 월매출 × 기준 영업이익률

상환 후 잔여 현금
= 기준 월이익 - 대표 월 상환액 - 추가 월 고정비

손익분기 추가 매출
= 현금 부족액 / 공헌이익률
~~~

지원하는 대출 상환 방식은 다음과 같습니다.

- 원리금균등 상환.
- 원금균등 상환.
- 만기일시 상환.
- 거치 기간 적용.

계산 결과에는 대표 월 상환액, 추가 고정비, 상환 후 잔여 현금, 손익분기에 필요한 추가 매출, 추가 주문 수와 위험 수준이 포함됩니다.

검증된 추가 순현금 가정이 없는 투자금 회수 기간은 숫자를 임의로 생성하지 않고 `UNAVAILABLE`로 반환합니다.

### 6. LLM의 역할

LLM은 진단 결과, 자금 배분 비율 또는 재무 수치를 결정하지 않습니다.

앞 단계에서 계산한 구조화 데이터를 입력받아 다음 내용을 설명하는 역할만 담당합니다.

- 어떤 병목이 해당 배분안에 영향을 주었는가.
- 자금이 각 카테고리에 배분된 이유는 무엇인가.
- SCB 참고 영역과 어떤 방향으로 연결될 수 있는가.
- 과거 회차에서 확인된 부작용이 있는가.

LLM 응답은 JSON 구조로 제한하며 앞 단계의 계산값을 수정할 수 없습니다.

LLM 호출이 실패하면 시뮬레이션 생성을 실패 처리해 설명이 없는 불완전한 결과가 저장되지 않도록 합니다.

### 7. 결과 검증 모델

집행 후 실제 성과가 입력되면 사전·사후 지표와 병목을 비교합니다.

~~~text
사전에는 있었지만 사후에는 없음 → 해결된 병목
사전과 사후에 모두 있음          → 지속 병목
사후에 새로 등장함               → 신규 병목
비교 데이터가 부족함             → 비교 불가
~~~

지표별 결과는 다음 세 값을 기준으로 판정합니다.

- 목표값.
- 손익분기값.
- 실제 관측값.

~~~text
실제값 ≥ 목표값
→ ABOVE_EXPECTED

손익분기값 ≤ 실제값 < 목표값
→ WITHIN_RANGE

실제값 < 손익분기값
→ BELOW_EXPECTED

판정 근거 부족
→ NOT_COMPARABLE
~~~

지표 변화와 자금 배분 사이의 인과관계를 단정하지 않습니다. 실제 결과에는 외부 환경 변화가 함께 영향을 줄 수 있음을 명시합니다.

### 8. 회차 이력 기반 개인화

회차 이력은 다음 시뮬레이션에 세 가지 방식으로 활용할 수 있습니다.

#### 개인 기준선

연구 파이프라인에서는 과거 3개 회차 이상의 실측 데이터가 쌓이면 원가율, 인건비율과 재구매율을 일반 업계 가정치가 아닌 해당 사업자의 과거 평균과 비교할 수 있습니다.

현재 백엔드 진단 API는 저장된 전체 상권 기준을 사용하며, 개인 기준선 진단의 완전한 연결은 후속 작업입니다.

#### 지속 병목 가중치

같은 병목이 2회 이상 연속으로 발생하면 관련 카테고리의 최소 배분 비중을 5%에서 15%로 높입니다.

#### 부작용 이력

특정 카테고리에 자금을 배분한 다음 회차에서 새로운 병목이 발생했다면, 이후 같은 카테고리를 포함하는 배분안의 설명에 경고를 추가합니다.

이 개인화 과정은 새로운 머신러닝 모델이 아니라 결과를 재현할 수 있는 결정론적 규칙입니다.

### 모델 검증

#### 병목 진단 시나리오 검증

의도적으로 병목을 포함한 합성 데이터 5종으로 진단 모델을 실행한 결과, 모든 사례에서 설계한 병목이 가장 높은 심각도로 탐지되었습니다.

| 검증 사례 | 기대 병목 | 결과 |
|---|---|---|
| 저녁 매출 부족 | 시간대별 고객 유입 부족 | 일치 |
| 원가 과다 | 높은 원가율 | 일치 |
| 인건비 과다 | 높은 인건비 비중 | 일치 |
| 좌석 포화 | 처리 용량 부족 | 일치 |
| 재구매율 저조 | 낮은 재구매율 | 일치 |

~~~text
합성 검증 정확도 = 5/5
~~~

이는 실제 사업장 전체에 대한 일반화 정확도가 아닙니다. 설계한 핵심 규칙이 의도한 대로 동작하는지를 확인한 단위 시나리오 검증입니다.

온라인 채널 병목은 현재 이 다섯 개 검증 사례에 포함되지 않습니다.

검증 과정에서 탐지된 병목의 근거 구성은 다음과 같습니다.

| 근거 | 비중 |
|---|---:|
| 실제 공공데이터 기반 | 20% |
| 업계 가정치 기반 | 60% |
| 사용자 합성 데이터 기반 | 20% |

이 비중은 다섯 개 합성 검증 사례에서 탐지된 병목을 기준으로 계산한 값이며, 전체 운영 데이터의 분포를 의미하지 않습니다.

#### 회귀모델 실험과 기각

유동인구와 신규 점포 비율로 다음 분기 매출 성장률을 예측하는 선형회귀 모델도 실험했습니다.

~~~text
입력값
- 유동인구.
- 신규 점포 비율.

예측값
- 다음 분기 매출 성장률.

실험 결과
- R² = 0.008.
~~~

설명력이 사실상 없는 수준이었기 때문에 이 회귀모델은 제품의 매출 예측에 사용하지 않았습니다.

데이터가 부족한 상태에서 그럴듯한 성장률을 만들어내기보다, 검증 가능한 병목 진단과 재무 계산에 집중하는 방향을 선택했습니다.

### 재현성과 버전 관리

AI 엔진의 결과가 어떤 기준으로 생성되었는지 추적할 수 있도록 다음 버전을 결과에 함께 저장합니다.

- 벤치마크 버전.
- 병목 진단 버전.
- 배분안 생성 버전.
- 재무 계산 버전.
- LLM 프롬프트 버전.

모델이나 계산 공식을 변경할 때 버전을 함께 갱신해 과거 시뮬레이션 결과의 계산 기준을 확인할 수 있도록 설계했습니다.

## 로컬 실행

### 요구 사항

- Node.js 22.12 이상.
- pnpm 10.28 이상.
- Python 3.13.
- uv.
- Docker 또는 PostgreSQL 15 이상.

### 저장소 복제

~~~bash
git clone https://github.com/youtheyeon/2026-KB-AI-Challenge.git
cd 2026-KB-AI-Challenge
~~~

### 백엔드 실행

~~~bash
cd backend
cp .env.example .env
uv sync --locked --dev
docker compose up -d postgres
uv run alembic upgrade head
uv run uvicorn app.main:app --reload
~~~

백엔드는 기본적으로 `http://127.0.0.1:8000`에서 실행됩니다.

- 상태 확인 API는 `GET /health`입니다.
- OpenAPI 문서는 `http://127.0.0.1:8000/docs`에서 확인할 수 있습니다.
- 시뮬레이션의 LLM 설명 생성에는 `ANTHROPIC_API_KEY`가 필요합니다.

`backend/.env`에 다음 값을 추가해 LLM 설명 생성을 활성화할 수 있습니다.

~~~dotenv
ANTHROPIC_API_KEY=your_api_key
~~~

실제 키는 저장소에 커밋하지 않습니다.

### 프론트엔드 실행

~~~bash
cd frontend
corepack enable
pnpm install --frozen-lockfile
pnpm dev
~~~

Vite가 출력한 로컬 주소로 접속하면 샘플 데이터를 사용해 전체 사용자 흐름을 체험할 수 있습니다.

현재 프런트엔드는 샘플 데이터 중심으로 동작하며, 백엔드 API와의 실제 연결은 후속 작업입니다.

### AI 모델링 실험

K-means 모델을 다시 실행하려면 별도 Python 가상환경에 연구용 의존성을 설치합니다.

~~~bash
cd ai
python3 -m venv .venv
source .venv/bin/activate
pip install numpy scikit-learn requests python-dotenv
python clustering.py
~~~

저장된 공공데이터를 사용하므로 클러스터링만 다시 실행할 때는 외부 API 키가 필요하지 않습니다.

공공데이터를 새로 수집하려면 다음 환경변수가 필요합니다.

~~~dotenv
SBIZ_SERVICE_KEY=your_service_key
SEOUL_API_KEY=your_api_key
~~~

전체 AI 시뮬레이션에서 LLM 설명까지 생성하려면 `ANTHROPIC_API_KEY`도 필요합니다.

| `POST` | `/api/simulations/{simulationId}/outcomes` | 예상 대비 실제 결과를 생성합니다. |
| `GET` | `/api/simulations/{simulationId}/outcomes` | 저장된 결과 검증 내용을 조회합니다. |
| `GET` | `/api/businesses/{businessId}/dashboard` | 회차별 이력과 다음 조건을 조회합니다. |

## 테스트

### 백엔드

~~~bash
cd backend
uv run pytest
uv run ruff check .
uv run ruff format --check .
~~~

PostgreSQL 통합 테스트는 `public` 스키마를 초기화하므로 반드시 격리된 테스트 데이터베이스를 사용해야 합니다.

데이터베이스 이름은 `_test`로 끝나야 하며 파괴적 초기화 동의를 명시해야 합니다.

~~~bash
ALLOW_DESTRUCTIVE_TEST_DATABASE_RESET=1 \
TEST_DATABASE_URL=postgresql+psycopg://postgres@localhost:5432/kb_ai_challenge_test \
uv run pytest
~~~

운영 또는 공유 데이터베이스 주소를 `TEST_DATABASE_URL`에 사용하지 않습니다.
